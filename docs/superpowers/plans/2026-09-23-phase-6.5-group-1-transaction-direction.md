# Phase 6.5 — Grupo 1 (`Transaction`: direção, tipo e transferência) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tornar a direção (entrada/saída) e o tipo (`Regular`/`Transfer`/`Adjustment`) propriedades explícitas da `Transaction`, com migration e backfill, e reescrever todas as agregações para dependerem delas em vez de `Category.Kind` — sem mudar o comportamento visível para transações existentes.

**Architecture:** O domínio ganha `TransactionDirection` e `TransactionKind`. Para transações `Regular` a direção continua a ser derivada do tipo da categoria (é o comportamento atual, agora gravado); transações sem categoria passam a ser um estado legítimo (`CategoryId = null`) com direção própria, substituindo o sentinel `Guid.Empty`. Migration adiciona `direction`, `kind`, `transfer_id`, torna `category_id` nullable, faz backfill e acrescenta CHECKs. Totais, donut, filtro por tipo, export e orçamentos passam a ler `Kind`/`Direction`. As fábricas de transferência e de acerto ficam para os grupos 3 e 4, que as testam.

**Tech Stack:** .NET 10, EF Core + Npgsql, Wolverine, PostgreSQL 16, Angular 21 + PrimeNG, xUnit/FluentAssertions/Testcontainers, Karma/Jasmine.

**Spec:** `specs/2026-09-23-phase-6.5-transfers-credit-card/` (`plan.md` §1, `requirements.md` D2–D4, D10; `docs/adr/ADR-014-transfers-and-account-balance.md`).

## Rulings de desenho (decididos ao escrever este plano)

- **R1 — `Regular` pode não ter categoria.** O spec D3 dizia "categoria obrigatória para `Regular`". O materializer de recorrentes já cria transações sem categoria (hoje com `Guid.Empty`, que as faz desaparecer dos totais). Tornar isso um estado legítimo (`CategoryId = null`, direção explícita) corrige o bug em vez de o esconder. CHECK na DB: `kind = 0 OR category_id IS NULL` (transferências e acertos nunca têm categoria). Custo se errado: um CHECK a apertar mais tarde.
- **R2 — Recorrente sem categoria materializa como saída** (`Outflow`). A `RecurringRule` não tem direção própria; a esmagadora maioria das recorrentes são despesas. Custo se errado: uma receita recorrente sem categoria aparece como despesa até ser categorizada (hoje nem aparece).
- **R3 — Direção de `Regular` = tipo da categoria**, também no import (comportamento atual preservado). A inferência pelo sinal da linha fica para o grupo 7 (spec §E).
- **R4 — Fábricas `CreateTransferLeg`/`CreateAdjustment` ficam para os grupos 3/4.** Aqui só o enum, a coluna e os CHECKs.
- **R5 — Donut por categoria ignora transações sem categoria** (não há fatia "Sem categoria" nesta fase); summary inclui-as.

## Review Focus

1. **Backfill sobre dados reais**: transações cuja categoria foi arquivada, cuja `category_id` é `Guid.Empty`, ou cuja `category_id` aponta para uma categoria que não existe (não há FK) — cada uma tem de acabar com direção coerente e sem violar CHECKs. Teste em Task 2.
2. **Recategorizar para uma categoria do tipo oposto** (despesa → receita) tem de inverter a direção e mover o valor de "despesas" para "receitas" no summary. Teste em Task 3.
3. **Filtro por `categoryIds` com `category_id` nullable**: filtrar por uma categoria nunca pode devolver transações sem categoria nem rebentar a tradução SQL. Teste em Task 3.
4. **Transação sem categoria no ecrã de transações e no dashboard**: aparece com "Sem categoria", sinal e cor pela direção, e o diálogo de edição não rebenta. Teste em Task 4.
5. **Orçamento com transação de outro tenant ou apagada**: o progresso continua a considerar só transações `Regular`, `Outflow`, do tenant, não apagadas. Coberto em Task 3 (teste de orçamento).
