# Phase 6.5 — Grupo 5 (Definições e vista do cartão de crédito) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Contas `CreditCard` ganham definições opcionais: limite de crédito, dia de fecho do extrato, dia de pagamento e conta de pagamento. Uma página própria mostra a dívida atual, o limite, o disponível, o ciclo corrente (gastos, pagamentos, movimentos), o extrato anterior (dívida no fecho) e o próximo pagamento previsto (valor e data). Tudo é calculado a partir das definições e das transações; nada de extrato é persistido.

**Architecture:**
- **Domínio:** um owned type `CreditCardSettings` em `Account` (nullable, só `CreditCard`); um calendário puro `CreditCardCalendar` (datas de fecho e pagamento, ciclo de uma data); um calculador puro `CreditCardStatementCalculator`.
- **Persistência:** migration `AddCreditCardSettings` com cinco colunas nullable em `financial.accounts` e CHECKs. Sem tabela nova, por isso o RLS existente de `accounts` já cobre as colunas.
- **Application:** Create/Update de conta recebem as definições. Uma query nova `GetCreditCardViewQuery` junta o saldo (grupo 2), o saldo no último fecho e os movimentos do período (query nova `ICreditCardActivityQuery`, implementada em Infrastructure) e chama o calculador. Endpoint `GET /api/financial/accounts/{id}/credit-card`.
- **UI:** as definições entram no dialog de conta quando o tipo é Cartão. Página nova `/app/accounts/:id/credit-card`, aberta por um botão na linha do cartão.

**Tech Stack:** .NET 10, EF Core + Npgsql (owned types, migrations por módulo), Wolverine (`[NonTransactional]`), PostgreSQL 16, Angular 21 + PrimeNG (`p-progressBar`, `p-table`), xUnit/FluentAssertions/Testcontainers, Karma/Jasmine.

## Rulings de desenho

Decididos com o utilizador em 2026-09-23 (Q1–Q3) e ao escrever este plano (R1–R8).

- **Q1 — Dia de fecho que não existe no mês → dia 1 do mês seguinte** (decisão do utilizador; substitui a proposta "último dia" da *Open question 3*). Ex.: fecho 31 → fevereiro fecha a 1/03, abril a 1/05; março fecha a 31/03. A mesma regra vale para o dia de pagamento.
- **Q2 — Pagamento no mês a seguir ao fecho se `PaymentDueDay ≤ StatementClosingDay`, senão no próprio mês** (decisão do utilizador). O "mês" é o **mês nominal do ciclo**, não o mês da data de fecho já transbordada. Ex.: ciclo de fevereiro com fecho 31 e pagamento 10: fecha a 1/03, paga a 10/03.
- **Q3 — Próximo pagamento previsto = max(0, dívida no último fecho − pagamentos recebidos desde esse fecho)**, com a data de pagamento desse extrato (decisão do utilizador). O grupo 6 acrescenta as prestações.
- **R1 — Ciclo nominal M = (fecho(M−1), fecho(M)]**, com os dois extremos por data e o dia do fecho incluído. O ciclo corrente de uma data T é o primeiro M com `fecho(M) ≥ T`, procurado a partir de `M = mês(T) − 1`: com fecho 31, T = 1/03 ainda pertence ao ciclo de fevereiro.
- **R2 — "Gastos do ciclo" = Σ `Regular` `Outflow` − Σ `Regular` `Inflow` no ciclo** (reembolsos abatem). "Pagamentos recebidos" = Σ `Transfer` `Inflow`. Acertos (`Adjustment`) e transferências de saída do cartão não contam em nenhum dos dois, mas contam no saldo e, por isso, na dívida.
- **R3 — Dívida = max(0, −saldo). Disponível = limite + saldo, sem clamp**: fica negativo se o cartão passou o limite, que é informação útil. No extrato anterior, a dívida no fecho = max(0, −saldo à data do fecho), com o saldo a data do grupo 2 (inclusivo).
- **R4 — Datas dos movimentos por data UTC de `occurred_at`**, a mesma convenção do corte de saldo do grupo 2 e do backlog `2026-09-23-convencao-dia-financeiro.md`. "Hoje" = data UTC.
- **R5 — `PaymentAccountId` é soft reference sem FK:** validada no handler (conta do tenant, não `CreditCard`, não a própria). É o padrão das referências a contas no módulo (ex.: `RecurringRule.AccountId`) e evita a configuração de FK a partir de um owned type. Se a conta de pagamento for arquivada, a vista mostra-a como `null`.
- **R6 — PUT de conta substitui as definições:** `creditCard: null` num PUT de cartão remove-as. Mudar o tipo de `CreditCard` para outro limpa-as. Enviar definições com tipo ≠ `CreditCard` → 400.
- **R7 — `GET /credit-card` sobre conta que não é cartão → 400** (`AccountNotCreditCardException`). Conta de outro tenant ou inexistente → 404. Cartão sem definições → 200 com `settings`, ciclos e próximo pagamento a `null` (só saldo e dívida), e a UI convida a configurar.
- **R8 — A lista de movimentos do ciclo na página vem do `GET /api/financial/transactions` existente** (`accountIds`, `dateFrom`, `dateTo`), não do endpoint do cartão. O endpoint devolve só agregados.

## Review Focus

1. **Transbordo de fecho:** fecho 31 em fevereiro/abril (1/03, 1/05), fecho 30 em fevereiro, fecho 29 em fevereiro bissexto (29/02) e não bissexto (1/03); o ciclo corrente de 1/03 com fecho 31 é o de fevereiro.
2. **Ciclo a atravessar o ano:** fecho 20 a 5/01 → ciclo 21/12–20/01, extrato anterior 21/11–20/12 e pagamento de dezembro em janeiro.
3. **Transferências recebidas não contam como gasto:** um pagamento do cartão feito a partir da conta à ordem baixa a dívida e o próximo pagamento, mas não os "gastos".
4. **Mudar o tipo de conta:** um cartão com definições que passa a Conta à ordem deixa as colunas todas a NULL (senão o CHECK rebenta com 500).
5. **Multi-tenancy:** `GET /credit-card` de uma conta de outro tenant → 404; conta de pagamento de outro tenant → 400/404, nunca ligada.

```csharp
/// Ciclo nominal (Year, Month): (fecho do mês anterior, fecho deste mês], datas inclusivas.
public sealed record CreditCardCycle(int Year, int Month, DateOnly Start, DateOnly End, DateOnly PaymentDueDate);

public static class CreditCardCalendar
{
    /// Dia `day` do mês; se não existe → dia 1 do mês seguinte (Q1).
    public static DateOnly DayOrNextMonthStart(int year, int month, int day)
    {
        var days = DateTime.DaysInMonth(year, month);
        return day <= days ? new DateOnly(year, month, day) : new DateOnly(year, month, 1).AddMonths(1);
    }

    public static DateOnly ClosingDate(int year, int month, int closingDay)
        => DayOrNextMonthStart(year, month, closingDay);

    /// Q2 — mês nominal do ciclo; pagamento no mês seguinte se dueDay ≤ closingDay.
    public static DateOnly PaymentDueDate(int year, int month, int closingDay, int dueDay)
    {
        var nominal = new DateOnly(year, month, 1);
        var dueMonth = dueDay <= closingDay ? nominal.AddMonths(1) : nominal;
        return DayOrNextMonthStart(dueMonth.Year, dueMonth.Month, dueDay);
    }

    public static CreditCardCycle Cycle(int year, int month, int closingDay, int dueDay)
    {
        var previous = new DateOnly(year, month, 1).AddMonths(-1);
        var start = ClosingDate(previous.Year, previous.Month, closingDay).AddDays(1);
        var end = ClosingDate(year, month, closingDay);
        return new CreditCardCycle(year, month, start, end, PaymentDueDate(year, month, closingDay, dueDay));
    }

    /// R1 — primeiro ciclo cujo fecho é ≥ date, a começar no mês anterior ao de `date`.
    public static CreditCardCycle CycleContaining(DateOnly date, int closingDay, int dueDay)
    {
        var candidate = new DateOnly(date.Year, date.Month, 1).AddMonths(-1);
        while (ClosingDate(candidate.Year, candidate.Month, closingDay) < date)
        {
            candidate = candidate.AddMonths(1);
        }
        return Cycle(candidate.Year, candidate.Month, closingDay, dueDay);
    }

    public static CreditCardCycle Previous(CreditCardCycle cycle, int closingDay, int dueDay)
    {
        var previous = new DateOnly(cycle.Year, cycle.Month, 1).AddMonths(-1);
        return Cycle(previous.Year, previous.Month, closingDay, dueDay);
    }
}

/// Movimento já reduzido ao necessário: data UTC, tipo, direção, valor (> 0).
public sealed record CreditCardMovement(DateOnly Date, TransactionKind Kind, TransactionDirection Direction, decimal Amount);

public sealed record CreditCardCycleTotals(CreditCardCycle Cycle, decimal Spent, decimal PaymentsReceived);

public sealed record CreditCardStatement(
    CreditCardCycleTotals CurrentCycle,
    CreditCardCycleTotals PreviousCycle,
    decimal PreviousClosingDebt,   // R3 — max(0, −saldo no fecho anterior)
    decimal CurrentDebt,           // R3 — max(0, −saldo atual)
    decimal Available,             // R3 — limite + saldo atual (sem clamp)
    DateOnly NextPaymentDueDate,   // Q3 — data de pagamento do ciclo anterior
    decimal NextPaymentAmount);    // Q3 — max(0, PreviousClosingDebt − CurrentCycle.PaymentsReceived)

public static class CreditCardStatementCalculator
{
    public static CreditCardStatement Calculate(
        CreditCardSettings settings,
        DateOnly today,
        decimal currentBalance,
        decimal balanceAtPreviousClose,
        IReadOnlyCollection<CreditCardMovement> movements);
    // current  = CreditCardCalendar.CycleContaining(today, closing, due)
    // previous = CreditCardCalendar.Previous(current, closing, due)
    // Totals(cycle): movimentos com Start <= Date <= End;
    //   Spent = Σ Regular Outflow − Σ Regular Inflow; PaymentsReceived = Σ Transfer Inflow (R2).
}
```
