# Phase 6.5 — Grupo 3 (Transferências entre contas) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Uma transferência é um par de `Transaction`s ligadas por `TransferId` (`Kind = Transfer`, sem categoria): perna de saída (`Outflow`) na conta de origem, perna de entrada (`Inflow`) na conta de destino. Criar, editar e apagar atua sempre nas duas pernas atomicamente; uma perna isolada não pode ser editada/apagada pelo fluxo normal de transações. Uma transação `Regular` existente pode ser convertida numa perna (ligando a uma contraparte já existente ou criando-a). Os totais (grupo 1) já ignoram `Transfer` por construção; o saldo (grupo 2) já soma todos os tipos — este grupo não toca nenhum dos dois, só cria as transações que os alimentam.

**Architecture:** Novo `Features/Transfers/` na Application, espelhando `Features/Transactions/`. `Transaction` ganha quatro membros novos: uma factory (`CreateTransferLeg`), dois métodos de mutação restritos a `Kind = Transfer` (`UpdateTransferLeg`, `ArchiveTransferLeg`) e um conversor (`ConvertToTransferLeg`, restrito a `Kind = Regular`). `Archive()` (o método genérico, chamado por `ArchiveTransactionCommand`) ganha uma guarda que recusa pernas de transferência — acertos (`Adjustment`, grupo 4) continuam arquiváveis por aí. Atomicidade: **este módulo não usa transações de BD explícitas** — todos os handlers de `Financial.Application` têm `[NonTransactional]` (opt-out da wrapper transacional do Wolverine) e confiam em `DbContext.SaveChangesAsync()` ser atómico para tudo o que está *tracked* nessa chamada (confirmado em `RecategorizeTransactionsHandler`, que já faz `N` updates + 1 `SaveChangesAsync`). Os handlers de transferência seguem o mesmo padrão: validam tudo (contas existem, são diferentes, moeda/`AmountIn` coerente) **antes** de construir qualquer `Transaction`, constroem as duas pernas, e fazem `AddAsync` × 2 + `SaveChangesAsync` × 1 — nada é escrito se a validação falhar mais cedo.

**Tech Stack:** .NET 10, EF Core + Npgsql, Wolverine (`[NonTransactional]`), FluentValidation (já usado no módulo — `FIN.Api/Validators/FinancialValidators.cs` já existe, não é infraestrutura nova), PostgreSQL 16, Angular 21 + PrimeNG, xUnit/FluentAssertions/Testcontainers, Karma/Jasmine.

**Spec:** `specs/2026-09-23-phase-6.5-transfers-credit-card/` (`plan.md` §3; `requirements.md` D1, D9 (contexto — o matching automático é do grupo 7), D10, D12; `docs/adr/ADR-014-transfers-and-account-balance.md`).

## Rulings de desenho (decididos ao escrever este plano)

- **R1 — "Não encontrado" em transferências usa `EntityNotFoundException` (`Sextante.Infrastructure.ErrorHandling`), não `ArgumentException`.** `GlobalExceptionHandler.cs:77-81` já mapeia `KeyNotFoundException`/`EntityNotFoundException` → 404, mas nenhum handler do `Financial` a usa hoje — todos lançam `ArgumentException("Conta não encontrada.", ...)`, que cai no `_ => 500` (`GlobalExceptionHandler.cs:95-99`, bug pré-existente, já catalogado como minor pendente das revisões dos grupos 1/2, fora do scope corrigir os call sites antigos). Este grupo introduz código novo; usa-se `EntityNotFoundException` desde o início, sem replicar o bug. Custo se errado: nenhum — é estritamente melhor que a alternativa e não altera comportamento de código existente.
- **R2 — Moeda igual em ambas as contas: `AmountIn` (se enviado) é ignorado, nunca validado contra `AmountOut`.** Plan.md diz "`AmountIn` obrigatório se as moedas diferem, senão igual a `AmountOut`" — lido literalmente como "iguala-se a `AmountOut`", não "tem de ser igual". A UI (§3.3) só mostra o campo "valor recebido" quando as moedas diferem, por isso um `AmountIn` divergente em contas da mesma moeda só chegaria de um cliente não-UI; rejeitar seria mais uma fonte de erro 400 confuso do que proteção real. Custo se errado: baixo, revisitável sem quebrar contratos (endurecer a validação mais tarde não é breaking change para a UI atual).
- **R3 — `ConvertToTransferCommand` sem `CounterpartTransactionId`: só cria a contraparte automaticamente se as duas contas tiverem a mesma moeda.** O comando (por spec, `TransactionId, CounterpartAccountId, CounterpartTransactionId?`) não leva um segundo valor — não há como inferir corretamente um `AmountIn` para moedas diferentes sem adivinhar câmbio. Moedas diferentes sem contraparte existente → `TransferCounterpartCurrencyMismatchException` (400), a mensagem indica para ligar a uma transação existente ou usar "Nova transferência". `CreateTransferCommand` continua a ser o único caminho para criar um par multi-moeda do zero. Custo se errado: uma conversão automática cross-currency fica bloqueada até o grupo 7 (import) ou um pedido de produto futuro; nada de destrutivo.
- **R4 — Ligar a uma contraparte existente da mesma moeda exige montantes exatamente iguais** (`TransferCounterpartAmountMismatchException` se não); **moedas diferentes não validam montantes** (câmbio implícito, D1). Custo se errado: um par legítimo com uma pequena diferença por taxa bancária (mesma moeda) fica bloqueado — o utilizador usa "Nova transferência"/edita manualmente; revisitável com uma tolerância se aparecer um caso real.
- **R5 — `UpdateTransferCommand` não troca qual perna é saída/entrada.** Identifica a perna "saída" pela que já é `Outflow` e a "entrada" pela que já é `Inflow`; `FromAccountId`/`AmountOut` atualizam sempre a perna `Outflow`, `ToAccountId`/`AmountIn` a perna `Inflow`. Não há forma de inverter o sentido de uma transferência via update — apagar e recriar. Custo se errado: UX pior num caso raro (o utilizador trocou origem/destino ao criar); fácil de adicionar suporte a troca mais tarde sem quebrar o contrato atual.
- **R6 — "Sugestão de contraperna existente" (§3.3) reutiliza `ListTransactionsQuery`** (filtrada por conta-alvo + montante, no frontend), não uma query nova de matching. O algoritmo preciso de correspondência (janela de ±7 dias, D9) é trabalho do grupo 7 (import automático); aqui é uma pessoa a escolher de uma lista razoável, não um sistema a decidir sozinho. Custo se errado: lista de sugestões mais ruidosa que um algoritmo dedicado dar-ia — aceitável, é sempre uma escolha humana.
- **R7 — `TransactionResponse` ganha `CounterpartAccountId` (nullable, só para `Kind = Transfer`)**, resolvido com uma segunda query em lote (`GetCounterpartAccountIdsAsync`, não N+1) sobre a página já carregada — nunca uma query por linha. O export CSV ganha a coluna "Conta contraparte" pelo mesmo mecanismo (join direto na query de export, que já não é paginada).
- **R8 — `Archive()` genérico recusa só `Kind = Transfer`, não `Adjustment`.** Acertos (grupo 4) continuam arquiváveis pelo caminho normal de transações (`requirements.md` C: "podem ser apagados, reversão auditável") — só pernas de transferência exigem o fluxo dedicado, porque só elas têm uma contraparte que ficaria orfã.

## Review Focus

1. **Atomicidade real**: um `CreateTransferCommand` cuja segunda conta não existe (ou pertence a outro tenant) não deixa a primeira perna criada — a validação de ambas as contas acontece antes de qualquer `AddAsync`. Teste explícito: contar transações da conta de origem antes/depois de uma tentativa falhada.
2. **`Archive()` bloqueia pernas mas não acertos** — nenhuma regressão no futuro fluxo de `Adjustment` (ainda não existe neste grupo, mas o guard não pode assumir `Kind != Regular ⇒ bloqueado`, só `Kind == Transfer`).
3. **Totais/saldo**: criar uma transferência não move o `summary`/donut/orçamento (só `Regular` conta, grupo 1) mas move o saldo das duas contas (todos os tipos, grupo 2) — testes de integração explícitos para ambos, não assumidos.
4. **Multi-tenancy**: todas as operações de transferência (criar/ler/atualizar/apagar/converter) respeitam o filtro global de tenant do EF sem checagem manual — `EntityNotFoundException`/404 para uma conta ou transferência de outro tenant, nunca uma exceção que vaze dados.
5. **`ConvertToTransferCommand` sobre uma transação já `Transfer`/`Adjustment`** → 400, não uma conversão dupla nem um `TransferId` sobrescrito.
