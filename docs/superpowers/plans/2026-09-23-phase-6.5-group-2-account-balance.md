# Phase 6.5 — Grupo 2 (Saldo de conta + `OpeningBalanceDate` + saldo inicial negativo) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cada conta passa a ter um saldo atual calculado on-demand (`OpeningBalance + Σ SignedAmount` sobre transações de **todos os tipos**, desde `OpeningBalanceDate`), consultável hoje ou a uma data (`at=`). Contas `CreditCard` passam a aceitar saldo inicial negativo (dívida); as restantes continuam a exigir `≥ 0`, incluindo ao mudar de tipo.

**Architecture:** `Account` ganha `OpeningBalanceDate` (imutável como `OpeningBalance`, default "hoje" quando omitida). O saldo não é coluna materializada (D5) — uma query de agregação nova (`IAccountBalanceQuery`, Application + implementação em Infrastructure, no padrão de `IBudgetProgressService`/`BudgetProgressService`) calcula o saldo de todas as contas do tenant numa chamada (lista) e de uma conta com corte opcional por data (detalhe + endpoint dedicado). Ao contrário dos totais do grupo 1 (só `Kind = Regular`), o saldo soma **todos os tipos** — é exatamente o propósito de existirem transferências e acertos.

**Tech Stack:** .NET 10, EF Core + Npgsql, Wolverine, PostgreSQL 16, Angular 21 + PrimeNG, xUnit/FluentAssertions/Testcontainers, Karma/Jasmine.

**Spec:** `specs/2026-09-23-phase-6.5-transfers-credit-card/` (`plan.md` §2; `requirements.md` D5, D6, D7; ADR-014).

## Rulings de desenho (decididos ao escrever este plano)

- **R1 — `Account.Create` ganha `DateOnly? openingBalanceDate = null` (default "hoje"), não um parâmetro obrigatório.** Evita reescrever ~11 call sites em testes já verdes (`AccountTests.cs`, `RecurringRuleHandlerTests.cs`, `CreateTransactionHandler_MultiCurrencyTests.cs`, `AccountHandlers.cs`) para um valor que a maioria não testa; quem quiser uma data específica passa-a explicitamente. Custo se errado: baixo — é aditivo, dá para tornar obrigatório mais tarde sem quebrar chamadas que já passam o argumento.
- **R2 — O saldo assume `Transaction.Amount.Currency == Account.Currency`, sem conversão de câmbio na soma.** O domínio hoje permite (mas não obriga) que uma transação tenha moeda diferente da conta (`TransactionHandlers.Handle(CreateTransactionCommand...)` valida contra a allowlist ativa, não contra a moeda da conta); isso já é uma lacuna pré-existente fora do scope de D5/D6, coerente com D12 ("cartões em moeda única"). Custo se errado: o saldo de uma conta com transações em moeda diferente da sua fica incorreto — situação já hoje inconsistente noutros pontos do sistema (ex.: export não converte por conta); não é uma regressão introduzida por este grupo. Não resolver aqui; não abrir backlog — é a mesma lacuna já implícita no design de Phase 3.
- **R3 — `GetCurrentBalancesAsync` nunca faz uma query por conta.** Faz no máximo duas idas à BD: uma para as contas do tenant (`Id`, `Currency`, `OpeningBalance`, `OpeningBalanceDate`), outra para as transações do tenant com `OccurredAt >= min(OpeningBalanceDate)` de todas as contas — depois agrupa e corta por conta em memória (mesma técnica já usada em `BudgetProgressService` para volume pessoal). Ver Task 3 para a assinatura sugerida.
- **R4 — Rótulo "Dívida" na UI só quando `Type == CreditCard` e `CurrentBalance < 0`.** Nas restantes combinações mostra-se só o valor (a vermelho se negativo, sem prefixo).

## Review Focus

1. **O saldo soma todos os `Kind`** (`Regular`, `Transfer`, `Adjustment`), ao contrário dos totais do grupo 1 que só contam `Regular` — teste explícito com um de cada tipo inserido via superuser.
2. **`at=` corta por dia inclusivo**, não por instante: uma transação às 23:59 UTC do dia `at` conta; uma do dia seguinte não.
3. **Conta de outro tenant no endpoint de saldo → 404**, via filtro de tenant do EF (não checagem manual) — confirmar que não há fuga de saldo entre tenants.
4. **CHECK da migration não quebra dados existentes**: todas as contas não-`CreditCard` já têm `opening_balance_amount >= 0` hoje (constraint do domínio antes deste grupo), por isso o CHECK deve poder ser adicionado sem backfill de dados — confirmar com um teste que insere via superuser.
5. **Mudar tipo de `CreditCard` para outro com saldo inicial negativo → 400**, mudar entre quaisquer outros tipos continua sempre permitido.

```csharp
// Application/Features/Accounts/IAccountBalanceQuery.cs
public interface IAccountBalanceQuery
{
    // Saldo "hoje" de todas as contas do tenant atual — uma chamada, sem N+1.
    Task<IReadOnlyDictionary<Guid, Money>> GetCurrentBalancesAsync(CancellationToken cancellationToken);

    // Saldo de uma conta; null se a conta não existir ou não pertencer ao tenant
    // (o filtro global do EF já trata multi-tenancy, sem checagem manual).
    // at == null: sem corte superior. at == D: soma até ao fim do dia D (inclusive).
    Task<Money?> GetBalanceAsync(Guid accountId, DateOnly? at, CancellationToken cancellationToken);
}
```

```csharp
// AccountsContracts.cs — acrescentar
public sealed record GetAccountBalanceQuery(Guid AccountId, DateOnly? At);
public sealed record AccountBalanceResponse(Guid AccountId, DateOnly? At, Money Balance);

// AccountResponse ganha, no fim:
//   DateOnly OpeningBalanceDate, Money CurrentBalance
// CreateAccountCommand ganha, no fim:
//   DateOnly? OpeningBalanceDate = null
```

Sugestão de implementação para `AccountBalanceQuery` (Infrastructure) — evita N+1 (R3): uma query carrega `(Id, Currency, OpeningBalance.Amount, OpeningBalanceDate)` de todas as contas do tenant; uma segunda soma `SignedAmount` (`Direction == Inflow ? Amount.Amount : -Amount.Amount`) das transações do tenant com `OccurredAt >= menor OpeningBalanceDate entre as contas` (convertido via `DateOnly.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc)`, que converte implicitamente para `DateTimeOffset` — mesmo padrão já usado em `BudgetProgressService.cs:46-48`); o corte por conta (`OccurredAt >= OpeningBalanceDate da própria conta`) e o agrupamento por `AccountId` fazem-se em memória sobre as linhas já materializadas (poucas linhas, uso pessoal — mesma técnica de `BudgetProgressService`). **Não** fazer uma query por conta num loop. `GetBalanceAsync` para uma única conta é mais simples: filtra `Transactions` por `AccountId` e `OccurredAt >= OpeningBalanceDate`, com `OccurredAt < at.AddDays(1)` quando `at` é dado (corte inclusivo do dia).

`AccountHandlers.cs`:
- `Handle(CreateAccountCommand...)`: passar `command.OpeningBalanceDate` a `Account.Create`; a conta acabada de criar não tem transações — `ToResponse(account, account.OpeningBalance)` sem chamar a query de saldo.
- `Handle(UpdateAccountCommand...)`: injetar `IAccountBalanceQuery balances`; `ToResponse(account, await balances.GetBalanceAsync(account.Id, null, ct) ?? account.OpeningBalance)`.
- `Handle(GetAccountByIdQuery...)`: idem.
- `Handle(ListAccountsQuery...)`: injetar `IAccountBalanceQuery balances`; chamar `GetCurrentBalancesAsync` **uma vez**, mapear cada conta com `balances.TryGetValue(a.Id, out var bal) ? bal : a.OpeningBalance`.
- Novo: `Handle(GetAccountBalanceQuery query, IAccountRepository accounts, IAccountBalanceQuery balances, CancellationToken ct) -> AccountBalanceResponse?`: `GetByIdAsync` para confirmar existência/tenant; `null` → `null`; senão `new AccountBalanceResponse(query.AccountId, query.At, (await balances.GetBalanceAsync(query.AccountId, query.At, ct))!.Value)`.
- `ToResponse` passa a receber `(Account account, Money currentBalance)`.

`AccountsEndpoints.cs`: novo endpoint dentro do mesmo `group`:

```csharp
group.MapGet("{id:guid}/balance", async (Guid id, [FromQuery] DateOnly? at, IMessageBus bus, CancellationToken ct) =>
{
    var response = await bus.InvokeAsync<AccountBalanceResponse?>(new GetAccountBalanceQuery(id, at), ct);
    return response is null ? Results.NotFound() : Results.Ok(response);
});
```

(precisa de `using Microsoft.AspNetCore.Mvc;` para `[FromQuery]`, que o ficheiro ainda não importa.)
